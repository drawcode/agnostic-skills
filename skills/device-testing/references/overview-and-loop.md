# Device testing

Drive an attached Android phone or iPhone from the terminal with one command set: screenshot, read
the frame, compute coordinates, tap, prove the screen changed, screenshot again. `scripts/device.py`
finds the device and routes each command to that platform's backend. Every command has the same
arguments and output on every platform.

This skill knows no app, project or device. Those come from three layers above it:

| Layer | Holds | Where |
|---|---|---|
| config | device aliases, app ids, paths, input-server names | `~/.config/device-testing/config.env` ([config.example.env](../config.example.env)) |
| profile | an app's screen map: named steps with coordinates and the log line that proves each | a TSV named by `DEVICE_NAV_PROFILE` |
| add-on | an app's own commands (a detector for its dialogs, its debug overlay) and hooks | a `.py` named by `DEVICE_TESTING_ADDONS` |

A project wraps the base with its own command that sets those three; see
[extending.md](extending.md).

## The loop

```bash
D=<skills>/device-testing/scripts/device.py
$D devices                               # attached devices, platform, alias
$D --device <alias> check                # resolved config, app, nav profile, installed build
$D preflight                             # unlocked, awake, logs ready, app stopped, logs cleared
$D install <apk|ipa> --symbol MY_CONST   # refuses a build that predates the change
$D launch                                # waits until the app is in front
$D nav <step>                            # a named step from the profile, waiting on its evidence
$D tap 540 1200 --wait 'Opened.*Menu'    # an action is proven by a log line, not by exit 0
$D shot                                  # prints the path
$D log '<your tag>' 40
```

`--device` takes an alias (`DEVICE_<ALIAS>_SERIAL`), an adb serial or an iOS UDID, before the
command. Without it the only attached device is used, then `DEVICE_DEFAULT`; with several and no
default it fails rather than guess.
